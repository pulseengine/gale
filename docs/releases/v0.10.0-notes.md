# v0.10.0 — "Taken on Trust"

Every item in this release started as a sentence. A header comment saying bodies were
"lifted VERBATIM" from the verified source. A script comment saying it needed a
particular solver version. A region model whose documentation described tenant
isolation. A release plan whose `release:` field said which version a requirement
belonged to. Each was believed, none was checked, and four of them were false by the
time anyone looked.

This release is what happened when we looked.

## The falsification statement

**Claim under test:** the properties gale asserts about its own artifacts — that a
copy matches its original, that a gate tests current code, that a solver is sound,
that a region is unreachable from tenant code — are mechanically checkable, and where
they were not, they were wrong.

**It survived, and the cost of finding out was four gates that were green for a reason
that did not hold.** Two of those four were introduced in this release, by the work
that was auditing the other two.

1. `mpu-thin`'s header said its bodies were "lifted VERBATIM from
   plain/src/mpu_switch.rs (Verus+Kani verified)". Nothing compared them.
   `verus-strip --check` gates `src/` against `plain/`; no gate related `plain/` to the
   bench driver's copy of it. The copy had already drifted (gale#410, gale#411).
2. The Renode isolation gate — gale's main *execution* oracle — loads a **committed**
   ELF that nothing rebuilds. **11 of 17 fixtures were older than their own sources**,
   two by three months (gale#413).
3. The gate written to catch #2 never saw a single linked object: it derived their
   paths with a doubled directory segment, so every path resolved to nothing,
   `filter_map` discarded them, and it reported PASS. Its own negative control asserted
   the derived path *ended in* the right name, which the broken path also did
   (gale#417).
4. `required-contexts` **passed** on a runner with no `gh`, because it degrades rather
   than fails when branch protection cannot be read — losing the list-vs-protection
   drift check while reporting success, in the job whose purpose is "every required
   context can actually report" (gale#418).

## What shipped

**A privilege axis in the verified region model.** `rasr_for` emitted AP 3 or AP 6 and
nothing else — both grant unprivileged code exactly what privileged code gets. So while
the supervisor ran, including under the entering tenant's map, every byte it could
reach the tenant could reach too, and supervisor-private state was not *expressible*:
not the executor's task table, not the tick counter, not the region table itself.

`writable` keeps its meaning and `unpriv` joins it — `UNPRIV_SAME` / `UNPRIV_RO` /
`UNPRIV_NONE`, reaching AP 1, 2 and 5. `try_add_region` is `try_add_region_perm` with
`UNPRIV_SAME`, so no existing caller changed behaviour by a bit.

Four tracks agree, and the fourth is the one no proof reaches:

| track | result |
|---|---|
| Verus (SMT/Z3) | **1168 verified, 0 errors**, first run — P1–P4, B1–B4 and the covers lemmas all re-discharged over the wider state |
| Kani (SAT/CBMC) | **6/6**, including k5 (the emitted AP denies unprivileged access, decoded back out of the RASR) and **k6, its negative control** |
| `cargo test` | **8 new vectors** — and the reason they exist is that `mpu_switch` had *no* test-track coverage at all |
| **WL55 silicon** | matched pair: private arm **MemManage at 0x20008000, CFSR 0x82** (DACCVIOL + MMARVALID, MMFAR at the target); control arm reads the magic back, 0 faults |

That the hardware *honours* AP 1/5 is an ARMv7-M architectural fact, assumed exactly as
the `mpu_write` seam contract is. The matched pair is how it was discharged, and the
pair is the evidence — a lone fault proves the platform, not the marking.
(`REQ-OS-PRIVREGION-001`, `VER-OS-PRIVREGION-001`)

**The copy is gone.** `mpu-thin` now depends on the `gale` crate and exports
`gale::mpu_switch` itself; 312 lines of duplicated region logic deleted. There is
nothing left to lift, so "VERBATIM" stopped being a claim a reader has to take on
trust. Cost, measured on both arms on the same pinned layer: **+200 B `.text`**
standalone and in the fused core alike — the logic, not a per-composition cost.

**Two freshness gates, and one of them caught the other.** `object-freshness` already
covered committed `.o` files; `fixture-freshness` now covers the Renode `.elf`
fixtures, with the 11 stale ones on a ledger that fails in *both* directions — a new
stale fixture fails, and a ledgered one that stops being stale fails until it is
removed. Both declare their input sets narrow and say so in their own output: a STALE
row is always real, an `ok` row is not a guarantee.

**A soundness floor under the bit-vector proofs.** ordeal 0.2.0–0.22.0 bit-blasted
shifts and rotations incorrectly at non-power-of-two widths and could return `Unsat`
**with a certificate that re-checks** — the one failure mode a certificate-checking
pipeline structurally cannot see (GHSA-xfxf-qxr3-435x). gale's 12 `.smt2` files were
verified unaffected independently, including extract-derived widths; all are width 32.
`run.sh` now refuses below 0.22.1, and refuses a solver whose version it cannot read.

**The merge gate runs on our own hardware.** Nine of the 22 required contexts moved to
`pulseengine-ci-01`. They are ~9 job-minutes of work that had been queueing behind 34
Zephyr matrix jobs; one hosted job was measured **queued over two hours** while
self-hosted jobs beside it in the same workflow started in three minutes.

**The target model closed its V.** Board/SoC/device facts are defined once in the
spar/AADL model and generated, with a drift gate and an IWDG retarget validated on
STM32G474 and STM32F100. (`REQ-TARGET-MODEL-001`, `VER-TARGET-IWDG-001`)

## What this release does NOT claim

- **Not multi-tenant, and not mixed-criticality.** `REQ-OS-UNPRIV-001` is open: gust
  tenant code still runs **privileged**, so the memory boundary is advisory rather than
  enforced against a hostile tenant. The privilege axis makes supervisor-private state
  *expressible*; it does not make tenants unprivileged. `gust_iso_unpriv_probe` remains
  green *because* that gap is open.
- **The safety case has no criticality axis at all** — 92 mentions of ASIL-D across
  1063 artifacts, zero of ASIL-A/B/C, zero of QM, zero coexistence or decomposition
  artifacts. Asked whether gust can host ASIL-D beside ASIL-B and QM, the honest answer
  is no, and the plan for it is scoped across v0.11–v0.13 (gale#423).
- **`REQ-OS-MPUSHIP-001` moved to v0.11.0**, bound to `REQ-OS-UNPRIV-001` by its own
  sequencing clause rather than by a date. Its earlier deferral moved it without moving
  its precondition, which is why it needed moving again.
- **The soundness floor currently refuses on our own pin.** No varve layer ships ordeal
  ≥ 0.22.1 — `2026.09.3` carries 0.19.0 and the newest published layer carries 0.22.0,
  both affected (varve#214). A red gate that explains itself beats a green one that
  means nothing.
- **Moving the gates made the CI wait shorter and ours, not bounded.**
  `timeout-minutes` bounds run time, not queue time, and the shared pool has been
  measured at 74 minutes queued (rivet#1018). 17 `container:` jobs — 67% of compute —
  still cannot move at all (gale#419).
- **Fused core growth is real:** `.text` 8260 → 8756 and SRAM 4236 → 4588 B of the
  STM32F100RB's 8192 (51% → 56%) across the copy removal and the privilege axis.
  Segments stay disjoint and the seam set is unchanged.

## Correction, added 2026-10-06

Appended rather than edited: the claims above are what the release stated, and
striking one quietly would be the same move this release was written against.

**"`object-freshness` already covered committed `.o` files" was not true of all
of them.** A `gate-potency` audit found that both implementations —
`check-object-freshness.py` and the xtask port — enumerated committed objects
with the pathspec `benches/gust/drivers/**/*.o`. git's `**/` requires at least
one directory level, so an object committed at the **root** of `drivers/` never
matched. Exactly one is: `iso-core-fused-cm3.o`, the object linked into
`gust_iso.elf` and therefore into the Renode isolation gate — gale's main
execution oracle.

Measured: `**/*.o` returns 24 files, `*.o` returns 25. The gate was green on
**20 of 21** gated-or-listed objects and its own census could not report the
omission, because a census can only flag what the enumeration returns.

Three things made it invisible, and they are the part worth keeping:

1. **The two implementations agreed.** `kill-criteria.yml` runs both and
   requires agreement — a real cross-check, but one that catches only
   *divergent* bugs. These were ported from one another and shared the blind
   spot.
2. **Both self-tests passed throughout.** They asserted the comparator and the
   ledger arithmetic in both directions, and both were correct. Neither asserted
   that the **sweep was complete**.
3. **`BUILDERS` excluded `build-iso-core.sh` on a false premise** — a comment
   saying it "writes into a temp dir", when its `OUT` defaults to the drivers
   directory and it writes the committed object in place.

So the sentence in "What shipped" should be read as: `object-freshness` covered
every committed object **except the one at the root of the drivers directory**.
Fixed in gale#438, with the enumeration now negative-controlled against the real
repo in both directions. A second finding from the same audit — `data-overlap`
is required and gates 1 of 5 committed composed artifacts — is gale#439.

Nothing else in this release rested on that gate. The four tracks behind
`REQ-OS-PRIVREGION-001` (Verus 1168, Kani 6/6, 8 `cargo test` vectors, WL55
silicon) are independent of it, and the copy-removal and footprint numbers were
measured directly rather than inferred from a green gate.
