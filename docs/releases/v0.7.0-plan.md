# v0.7.0 — "Run It" (plan)

v0.6.0 ships an OS that composes into one signed component and **has never been run as
one**. Every claim in it is structural: one scheduler and one clock are verified by
import routing and source ownership, not by observing a handle survive a call. The 20 741
bytes are a wasm figure that implies nothing about code size, SRAM or cycles.

v0.7.0 turns structural claims into observed ones, or finds out they were wrong.

## The thesis, stated so it can fail

**Claim under test:** the fused `gale-nano` component behaves as one OS — a handle from
`spawn.start()` is valid in `timer.sleep()` and in `exec.state()`, and there is a single
clock behind `time.now()` and the timer's deadlines.

**This is a falsification target, not a demo.** We asserted it from import routing. If
running it refutes the claim, that is the most valuable result this release can produce
and it ships as the headline, exactly as the triplication finding did in v0.6.0.

## The execution ladder

Each rung is strictly stronger evidence than the one above it, and each is independently
shippable. Do them in order; do not skip to silicon because it sounds better.

| # | rung | what it converts | new evidence |
|---|---|---|---|
| E1 | Run the composite on a **host engine** | "one scheduler" from structural to observed | a handle crossing `spawn` -> `timer` -> `exec` |
| E2 | **Dissolve** the composite (fuse + optimise + lower) | the wasm figure into a native one | first real `.text`/`.bss` for the whole OS |
| E3 | Run the dissolved OS under **qemu / Renode** | behaviour under a cycle model | content gates on the composed OS, not per-provider |
| E4 | Run it on **silicon** (G474, F100) | the last inference | the composed OS on two dies |

E1 is cheap, fast, and carries the most claim-per-hour: it is the rung that can refute
the thesis. Start there and do not let it slip behind the more impressive-sounding rungs.

## Gates each rung must add

A rung is not done when it runs once. It is done when it cannot silently stop being true:

- **E1** — a test that starts a task, sleeps it via `timer`, and asserts `exec.state()`
  agrees; run in CI on every change to any provider.
- **E2** — the dissolved object's undefined symbols must be exactly the `gust:hal` seam,
  gated like `build-cross-arch.sh` does. A smaller object with no undefined symbols is
  the failure mode, not the win.
- **E3** — content gates on the composed OS, alongside the existing per-driver ones.
- **E4** — the silicon result recorded with its `n`, its unspliced-capture status, and
  what it does *not* evidence, in the style of `silicon/RESULTS-wdg-f100.md`.

## Carried forward from v0.6.0's stated gaps

These were disclosed at v0.6.0, not dropped. Each closes here or is re-stated with its
reason:

- **Stale objects** — `spawn-provider-cm3.o`, `timer-provider-cm3.o`, `os-ts-cm3.o`,
  `exec-cm3.o`, the last carrying a pending `poll_task` -> `poll-task` symbol-contract
  change. E2 forces this anyway.
- **witness MC/DC on the OS** — only meaningful once E1 exists: coverage of something
  executed, not of something composed. The tool is released and has never been pointed
  at this OS.
- **scry loop-bound inference** — closes the `reason=loop` gap in the WCET sidecars,
  which is the one thing standing between per-function bounds and a schedulability
  argument.
- **RV32 target model** — what a faithful RISC-V *execution* result actually needs. Six
  of eight drivers lower to RV32 today and none has been run; a target model is the
  prerequisite, not more backend work.
- **On-device hosting of replaceable tenants** — the migratable tier, and the half of
  "testable and migratable" that v0.6.0 did not touch.

## The feedback loop

The point of a loop is that evidence changes the plan, and that friction leaves the
building. v0.6.0 demonstrated both in a single day: a RISC-V blocker was filed as
synth#871 in the morning and fixed in synth 0.52.0 the same afternoon, which moved an
item off the WON'T list before the release shipped.

So, per rung:

1. **Run the rung.** Ground every claim in tool output.
2. **Update the ledger.** `docs/releases/*-notes.md` "does NOT claim" sections are the
   live statement of what we know. A rung that succeeds *removes* a line there; a rung
   that fails *rewrites* one. The ledger is never edited to look better.
3. **Route friction the same day.** A tool that errors, declines, or forces a workaround
   becomes an upstream issue with a repro *while the context is fresh* — synth, loom,
   meld, wac, wasm-tools. Unreported friction is friction the next rung re-hits.
4. **Re-derive, don't inherit.** Before a claim reaches a slide or a release note,
   re-check it against the live artifact. v0.6.0 caught two stale claims this way (a
   `RESULTS.md` blocked-on-synth#518 note that had quietly become false, and a silicon
   doc asserting a property the firmware never exercised).

### An input this release actually has

Research Day is 2026-08-06 and the room contains the people best placed to attack this:
compiler-correctness, Wasm semantics, formal methods, and industrial embedded. **Their
questions are v0.7.0 input, not applause.** Capture them the same week, triage them into
this plan, and let the ones that survive scrutiny reorder the ladder above.

The two open asks already carried into that room:

- **translation validation for the dissolve** — the trust moved from a runtime we do not
  ship into a compiler we do not verify, over an alphabet of exactly two effects.
- **what enforces isolation once `meld fuse --memory shared` collapses shared-nothing
  linking into one address space** — raised by a reviewer as the more interesting of the
  two, and unanswered.

## Not in scope

Anything that makes the OS bigger before it has been run once. New drivers, new
capabilities and new targets all wait behind E1. Breadth was v0.6.0's axis; this release
is depth on a single claim.
